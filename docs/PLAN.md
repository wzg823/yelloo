# 产品方案与路线图

---

## 1. 定位

**面向中文开发者的公开技术社区。**

一句话概括形态：**内部是 Discord 式的频道模型，对外是论坛式的 URL 结构。**

这个组合不是随意拼的，而是为了解决一个具体矛盾：

> 频道制的滚动时间线适合实时讨论，但**天然不利于搜索引擎收录**；
> 而公开技术社区最依赖的就是自然搜索流量——程序员遇到问题会去搜。

Discord 对这个矛盾的答案是"不做 SEO"（它是私密社群工具）。
我们不能这么做，所以：

| 层 | 采用 | 目的 |
|---|---|---|
| 数据模型 | 频道 → 连续消息流 + Thread | 实时讨论体验 |
| URL 结构 | `/c/[slug]`、`/m/[id]`、`?before=` 分页 | 让每条讨论都有可被收录的独立地址 |
| 渲染方式 | 服务端渲染真实 HTML（非客户端 fetch） | 爬虫能看到完整内容 |

## 2. 已确定的产品决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 产品形态 | **频道制（B）** | 实时讨论体验优先 |
| 实时方案 | **SSE**（非 WebSocket） | 只需单向推送；省掉重连与重放协议 |
| 社区结构 | **单一社区**，不做多服务器/邀请链接 | 公开社区不需要，还省掉整套权限复杂度 |
| 可见性 | 读**完全公开**（含游客），写需登录 | SEO 与获客的前提 |
| 注册 | 开放注册（不做邀请码） | 邀请码会掐死增长 |
| 部署地 | **中国大陆** | 访问速度；代价是备案（见 docs/DEPLOY.md） |
| 目标规模 | 单机起步，万级注册用户 / 千级日活 | 决定"先不引入什么" |
| 界面语言 | 简体中文 | — |

### 刻意不做的事

- **不做多租户**。没有"服务器/工会"概念，只有分类与频道
- **不做端到端加密**。公开社区的内容本就要可审核、可搜索
- **不做语音/视频**。技术社区的文字沉淀价值远高于语音，且语音是一整套新基础设施
- **不做 AI 功能**。曾评估过 Agent 接入方案，结论是它会把这个项目从"一个人三周"
  变成"小团队三个月"，且引入推理成本分摊、密钥托管、Agent 熔断等一整套复杂度。
  在核心闭环被真实用户验证之前，这些都是负担

## 3. 三种频道类型

不要所有频道都做成滚动时间线，否则内容和 SEO 都会退化：

| 类型 | 行为 | 用途 | SEO 策略 |
|---|---|---|---|
| `text` | 实时滚动流 | #闲聊、#求助 | 索引首屏 + 分页页 |
| `forum` | **每条顶层消息 = 一个独立帖子** | #作品分享、#问答 | **重点索引**，一帖一 URL |
| `announce` | 只读，仅管理可发 | #公告、#规则 | 索引 |
| `thread` | 从某条消息分叉出的子频道 | 长讨论 | 索引 |

> 当前实现：四种类型都已存在于数据模型，`announce` 的只读行为已生效。
> `forum` 的"一帖一 URL"与 `thread` 的自动创建属 **P3 未完成**（见第 7 节）。

## 6. 风险与对策

| 风险 | 具体表现 | 对策 |
|---|---|---|
| **备案卡住** | 域名无法解析到大陆服务器，项目实际无法上线 | **第一天就提交备案**；准备香港服务器作为 Plan B（配置无需改动） |
| 冷启动 | 社区没人发言 → 更没人来 | 先由发起人自己产出 20~30 条有价值的技术内容，再引入种子用户 |
| 垃圾广告泛滥 | 开放注册后被批量刷帖 | P2 的新人限流 + 举报通道 + 邮件验证 |
| 消息延迟数十秒 | 中间层缓冲 SSE | 部署验证清单里专门有一项；见 docs/EVENTS.md 第 7 节 |
| 连接泄漏 | `realtime.connections` 只增不减 | 监控该指标；代码上确保 `close()`/`cancel()` 两条路径都释放 |
| 单机故障 | 全站不可用 | 每日备份到对象存储 + 恢复演练；单机是 P0~P3 的合理取舍 |
| 数据库迁移不可回滚 | 发版后无法快速退版 | **迁移只做加法**；要删列分两个版本做（见 docs/DEPLOY.md 第 6 节） |
| Snowflake 纪元被改 | ID 失去单调性，分页与实时补齐全乱 | `.env` 里标注"有数据后不可改"；代码中已有注释 |
| Markdown XSS | 后台被拿下 | 白名单式渲染器（先转义再解析）；**换渲染器必须补 HTML 消毒** |
| 游标精度丢失 | 点击消息跳错页 | 全链路 BigInt/字符串约定，见 docs/DB.md 第 1.1 节 |

## 8. 不可妥协的约束（给未来的自己）

这十条是踩过的坑换来的。改动前请先确认没有违反：

1. **`messages.id` 必须保持 Snowflake bigint。** 改成 `bigserial` 或 `number`
   会依次导致 ID 精度丢失 → 跳错页 → 实时补齐漏消息
2. **JS 侧必须用 `BigInt`，出 JSON 必须转字符串。** 见 `src/lib/serialize.ts`
3. **`messages` 表只保留 `(channel_id, id DESC)` 这一个核心索引。**
   这是增长最快的表，多余索引直接拖慢写入
4. **`channels.message_count` / `last_message_at` 必须与消息插入同事务更新。**
   分开提交会让频道列表顺序永久错乱
5. **推进已读位点必须用 `greatest()`。** 否则并发下位点会倒退
6. **SSE 端点绝不能被缓冲。** 任何中间层的缓冲都表现为"消息延迟数十秒"
7. **服务端必须重新校验权限，不信前端隐藏按钮。** 每个写接口单独检查
8. **Markdown 输出必须先转义、再按白名单解析。** 不要依赖"记得配置消毒器"
9. **软删除时 API 层必须清空正文。** 只靠前端隐藏等于没删
10. **`NEXT_PUBLIC_*` 变量在构建期内联。** 改站点名必须重建镜像，重启无效
